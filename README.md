# Railtally

A personal companion web app (PWA) for a European train-route board game. Each player uses it on their own phone:
tap routes to mark who claimed them, track trains, stations and score, rotate the map for the other side of the table,
and keep a history of finished games. English and Turkish. Works offline.

> Unofficial fan-made companion app, not affiliated with Days of Wonder. The map is drawn from real geography in an
> original style; it contains no board artwork.

See [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for the design and [REMAINING_PLAN.md](REMAINING_PLAN.md) for what is left, in recommended order. The roadmap (ticket chooser, strategy builder and
real-time multiplayer come later).

## Privacy

Railtally has no accounts and no analytics. Games are stored only in the browser's IndexedDB on your
device; nothing is sent anywhere, unless you start a *shared game* (needs a sync server, see `server/`): then the public
board (players, claimed routes, stations) goes to that server. Tickets and strategy never leave your phone. Export/import backups are files you handle yourself.

## Develop

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # unit tests (Vitest)
npm run lint
npm run build      # type-check + production build (PWA)
npx playwright install chromium   # once
npm run e2e        # end-to-end tests on a phone viewport
```

## How it works

- **Event-sourced state.** The app stores a list of actions (`src/game/actions.ts`) and computes the game with a pure
  reducer (`src/game/reducer.ts`). Undo removes the last action; saving persists the list to IndexedDB. `src/game`
  has no React or browser code so a future multiplayer server can run the same reducer.
- **Map data** lives in `src/data/json` (cities, routes, tickets) and is checked by `tests/data.test.ts`.
  Please verify it against your physical board.
- **Sync adapter** (`src/sync`) hides where the action log is stored. Local games use `LocalAdapter` (IndexedDB); shared
  games use `RemoteAdapter` (server-ordered log, optimistic local changes, offline queue) over a WebSocket to the
  Cloudflare room in `server/`. `memory:` as sync URL runs a fake server in the page for tests.
- City label positions are precomputed (`src/ui/map/labelLayout.json`). After changing the map layout, regenerate
  them with `UPDATE_LABELS=1 npm test`.
- Icons are generated by `node scripts/make-icons.mjs`.

## Deploy

The output of `npm run build` is a static site in `dist/`; it needs HTTPS to install as a PWA and to run the service worker.

**GitHub Pages** (https://onurcem.github.io/railtally/), without a workflow file of our own:

```bash
scripts/deploy-pages.sh
```

It builds with `BASE_PATH=/railtally/` (the Vite `base`; PWA `start_url`, `scope` and icons follow it), then pushes
`dist/` plus `.nojekyll` to the `gh-pages` branch as a single commit with plain git. Pages was enabled once with
`gh api -X POST repos/OnurCem/railtally/pages -f 'source[branch]=gh-pages' -f 'source[path]=/'`.
Every publish triggers GitHub's built-in "pages build and deployment" run (uses Actions minutes), so deploy
deliberately. The working tree must be clean. Phones pick up a new version on their next online visit.

For a custom domain at the site root, build with `BASE_PATH=/` and add a `CNAME` file to `public/`.
`npm run e2e` tests the app under `/railtally/`; use `BASE_PATH=/ npm run e2e` to test at the root.
